# TCE — Tarik Context Engineering

> **TCE** = Тарик Шехипар (8 вопросов) + Контекстный инжиниринг + Codex CLI + NC777.

## Суть

Сырой запрос пользователя → 8 уточняющих вопросов Тарика Шехипара → собранный контекст → self-contained промпт для AI-кодера (Codex CLI, Claude Code, Hermes Agent, Crab и др.) с ролевой разметкой NC777.

Используется когда:
- Пользователь даёт размытую задачу («сделай парсер», «напиши бота», «пофикси баг»)
- Нужно подготовить задание для AI-агента с полным контекстом
- Нужно обеспечить, чтобы AI имел всю информацию без лишних вопросов
- Задача требует инженерии контекста — подвязки файлов, зависимостей, архитектуры

## Workflow

```
RAW REQUEST → 8 QUESTIONS → CONTEXT MAP → PROMPT → AI AGENT EXECUTES
```

### Шаг 1 — 8 вопросов Тарика Шехипара (адаптированные для задач)

Задай пользователю **только те вопросы, на которые ещё нет ответа** в его запросе:

| # | Вопрос | Цель |
|---|--------|------|
| Q1 | **Какой конкретный результат должен быть получен?** | Чёткая формулировка deliverable |
| Q2 | **Почему это важно / какая проблема решается?** | Мотивация и контекст |
| Q3 | **Как мы поймём, что задача выполнена успешно?** | Критерии приёмки |
| Q4 | **Как ты видишь архитектуру/подход?** | Path — предпочтения по реализации |
| Q5 | **Какой первый минимальный шаг?** | MVP / первый вертикальный срез |
| Q6 | **Какие ресурсы нужны?** (файлы, API, библиотеки, данные) | Зависимости |
| Q7 | **Какие подводные камни / что может пойти не так?** | Риски и edge cases |
| Q8 | **Какой контекст нужно передать?** (ссылки, спецификации, примеры) | Background |

**Правила:**
- Не задавай вопрос, если ответ уже есть в запросе
- Задавай по одному вопросу за раз
- Всегда задавай повторные/уточняющие вопросы, пока задача не будет полностью понята. Не переходи к генерации промпта, пока не собран полный контекст
- Если пользователь явно сказал «сделай сам» — **не задавай вопросов**, используй default-ответы (см. ниже)

### Шаг 2 — Контекстный инжиниринг (Context Engineering)

После получения ответов (или используя default-значения) собери **Context Map**:

```markdown
## GOAL
[одна строка — что делаем]

## CONTEXT / PROBLEM
[почему это нужно, какая проблема]

## SUCCESS CRITERIA
- [критерий 1]
- [критерий 2]
- [критерий 3]

## CONSTRAINTS
- [технические ограничения]
- [архитектурные решения]
- [стиль, conventions]

## FILE STRUCTURE / SCOPE
[какие файлы затрагиваются, какие создаются]

## DEPENDENCIES
[библиотеки, API, инструменты]

## RISKS
[топ-3 риска]

## EDGE CASES
[особые случаи, которые нужно обработать]
```

### Шаг 3 — Генерация промпта для Codex CLI

Сформируй финальный промпт:

```bash
codex exec -m gpt-5.3-codex -s danger-full-access \
  -c skip_git_repo_check=true \
  --dangerously-bypass-approvals-and-sandbox \
  "$PROMPT"
```

Где `$PROMPT` — self-contained текст:

```
# Task: [GOAL]

## Context
[CONTEXT]

## Files
- [file1.py]: [что в нём, зачем менять]
- [file2.js]: [что в нём]

## Requirements
1. [требование]
2. [требование]

## Success Criteria
- [ ] [критерий]
- [ ] [критерий]

## Constraints
- [ограничение]
- [ограничение]

## NC777 Pipeline
Roles: Prophet → Architect → Developer → QA → Cleaner

## Verification
[команды для проверки: сборка, тесты, линт]
```

### NC777 — Ролевая разметка в промпте

Добавь в промпт раздел с указанием, какие роли NC777 должны быть задействованы:

| Сложность | Роли | Когда |
|-----------|------|-------|
| 🟢 Простая | Developer → QA | 1 файл, < 50 строк |
| 🟡 Средняя | Prophet → Architect → Developer → QA → Cleaner | 2–5 файлов |
| 🔴 Сложная | Prophet → Architect → Reviewer → Developer → QA → Saboteur → Cleaner | >5 файлов, архитектурные изменения |

Формат:
```markdown
## NC777 Pipeline
Roles: Prophet → Architect → Developer → QA → Cleaner

Role contracts:
- **Prophet**: уточнить требования, выявить assumptions
- **Architect**: спроектировать решение до реализации
- **Developer**: реализовать по спецификации архитектора
- **QA**: проверить каждый критерий приёмки
- **Cleaner**: убрать мусор, временные файлы, комментарии
```

## Режимы работы

### Режим «Интерактивный» (по умолчанию)
Задаёшь 2–4 вопроса Тарика → получаешь ответы → строишь контекст → генерируешь промпт → предлагаешь запустить.

### Режим «Сделай сам» (когда пользователь сказал «сделай сам»)
Не задаёшь вопросы. Используешь default-значения:
- **Result**: явно вывести из запроса
- **Criteria**: «работает без ошибок, код читаемый, покрыты основные edge cases»
- **Approach**: «прагматичный, без овер engineered»
- **First step**: «минимальный рабочий прототип»
- **Resources**: из запроса + автоопределение через поиск файлов
- **Risks**: из анализа задачи
- **Context**: из поиска по репозиторию

### Режим «Supergoal» (сложные задачи, >1 часа)
Загрузи навык `supergoal` и передай задачу туда. TCE используется только для первичного уточнения.

## Пример вывода (режим «Сделай сам»)

```
## TCE Context Engineering Complete

### Context Map
**Goal**: Написать Telegram-бота для напоминаний о днях рождения
**Success Criteria**:
  1. Бот принимает команду /add и дату
  2. Отправляет уведомление в 9:00 в день рождения
  3. Работает с SQLite
**Dependencies**: python-telegram-bot, sqlite3, APScheduler

### Codex Prompt Ready
Команда для запуска:
codex exec -m gpt-5.3-codex -s danger-full-access \
  -c skip_git_repo_check=true \
  --dangerously-bypass-approvals-and-sandbox \
  "[промпт длиной N символов]"

NC777 Pipeline: Prophet → Architect → Developer → QA → Cleaner
```

## Библиотека методик — что нашёл в сети

В процессе исследования сети для улучшения TCE были найдены следующие методики, которые можно комбинировать с вопросами Тарика Шехипара:

### 1. GROW (Whitmore) — коучинговая классика

| Этап | Вопрос | Созвучность с Тариком |
|------|--------|----------------------|
| **G**oal | Чего ты хочешь достичь? | Q1 (Result) |
| **R**eality | Где ты сейчас? Какие препятствия? | Q7 (Risks) |
| **O**ptions | Какие варианты решений? | Q4 (Approach) |
| **W**ill | Что ты сделаешь прямо сейчас? | Q5 (First step) |

**Когда добавить в TCE**: после Q1–Q2 добавить Reality-check («а что уже есть/сделано?») — это снижает риск перепроектирования.

### 2. 5-Layer Context Stack (Phil Schmid / Google DeepMind, 2025)

Архитектура контекстного инжиниринга, которая стала стандартом в 2025–2026:

```
Layer 1: System Prompt     — Persona, Constraints, Core Instructions
Layer 2: Memory            — Short-term (history), Long-term (persistent facts)
Layer 3: Retrieval         — RAG, vector search, dynamic context injection
Layer 4: Tools & APIs      — Function calling, tool descriptions, schemas
Layer 5: Output Format     — JSON schema, markdown, structured output
```

**Что даёт TCE**: Твой текущий Context Map — это Layer 1 + Layer 5. Для сложных задач (🟡🔴) нужно явно добавлять Layer 3 (Retrieval — поиск по репозиторию, документации) и Layer 4 (Tools — указать какие API/библиотеки доступны).

### 3. Anthropic Context Engineering (2025)

Ключевые принципы от команды Anthropic:

- **Context Budgeting** — контекст конечен. Каждый токен в промпте крадёт место у ответа. Не включай ничего лишнего.
- **Progressive Disclosure** — давай минимальный контекст, позволяй агенту самому запрашивать детали по мере необходимости. Для Codex это значит: в промпте только ключевые файлы, остальное агент прочитает сам.
- **Component Thinking** — разделяй инструкции, контекст, инструменты и спецификацию выхода. Не мешай всё в одну кучу.
- **Systematic Evaluation** — проверяй каждую итерацию промпта.

**Что добавить в TCE**: раздел «Context Budget» — оценка длины промпта и удаление необязательного контента.

### 4. SMART — критерии приёмки

```
S — Specific (конкретный)
M — Measurable (измеримый)
A — Achievable (достижимый)
R — Relevant (релевантный)
T — Time-bound (ограниченный по времени)
```

**Что добавить в TCE**: проверять Success Criteria на SMART-совместимость перед передачей в Codex.

### 5. 5W2H — постановка задач

```
What?   — Что делаем?
Why?    — Зачем? (проблема)
Where?  — Где? (репозиторий, окружение)
When?   — Сроки?
Who?    — Для кого? (пользовательский сценарий)
How?    — Как? (технологии, подход)
How much? — Объём? (границы, что НЕ делаем)
```

**Что добавить в TCE**: вопрос «How much?» — явно указать границы задачи (что входит, что НЕ входит). Это снижает риск Codex-галлюцинаций.

### 6. SCQA (Minto Pyramid) — структура проблемы

```
S — Situation (ситуация как есть)
C — Complication (что пошло не так)
Q — Question (какой вопрос встаёт)
A — Answer (предлагаемое решение)
```

**Что добавить в TCE**: для баг-репортов и задач с неочевидной проблемой использовать SCQA как шаблон описания контекста.

## Сравнение методик

| Методика | Фокус | Сильная сторона | Слабая сторона |
|----------|-------|-----------------|----------------|
| **Тарик Шехипар** 8Q | Глубокое прояснение | Покрывает result → risks → gratitude | Медленная, не для быстрых задач |
| **GROW** | Действие | Быстрая, action-oriented | Не покрывает контекст и риски |
| **5-Layer Context Stack** | Архитектура контекста | Структура для сложных AI-систем | Требует технической зрелости |
| **Anthropic CE** | Экономия контекста | Прагматичная, production-ready | Не даёт вопросов для уточнения |
| **SMART** | Критерии | Жёсткая проверка достижимости | Не помогает с контекстом |
| **5W2H** | Полнота описания | Быстрая, универсальная | Поверхностная |
| **SCQA** | Проблема → решение | Структурирует баги и кейсы | Только для проблемных сценариев |

## Selection Guide — когда что использовать

| Ситуация | Основная методика | Дополнительно |
|----------|------------------|---------------|
| Размытая фича | **Тарик 8Q** (все 8) | SMART на критерии |
| Быстрый фикс / баг | **SCQA** для описания + **5W2H** для объёма | GROW на первый шаг |
| Новая фича, tech долг | **Тарик 8Q** (Q1–Q5) + **GROW** | 5-Layer для архитектуры |
| Сложная задача (🟡🔴) | **Тарик 8Q** + **5-Layer Context Stack** | Anthropic budgeting |
| «Сделай сам» | **5W2H** (вывести из запроса) + **SMART** | Context Budget |
| Критический баг в проде | **SCQA** → **GROW** (Will) | — |

## Контекстный инжиниринг — расширенная схема

При генерации промпта для Codex используй не просто плоский текст, а **5-слойную архитектуру** (если задача сложная):

```markdown
# LAYER 1: System Prompt (Persona + Constraints)
Ты — senior Python-разработчик. Используешь pep8, typing, pytest.
Не используешь сторонние библиотеки без явного указания.

## LAYER 2: Memory / State
Текущий проект: парсер Excel в JSON.
Уже реализовано: чтение .xlsx через openpyxl.
Предыдущие решения: pandas не подошёл (тяжёлый для 1M+ строк).

## LAYER 3: Retrieval / Context
Ключевые файлы:
  - src/parser.py: текущий парсер, 340 строк
  - tests/test_parser.py: тесты, 120 строк
  - examples/sample.xlsx: пример входных данных

## LAYER 4: Tools / APIs
Доступно: openpyxl, json, pathlib, re, logging
НЕ использовать: pandas, numpy, xlrd

## LAYER 5: Output Format
1. Модифицировать src/parser.py
2. Обновить тесты
3. Вывести diff
```

### Context Budgeting (Anthropic)

Перед отправкой промпта в Codex:

1. **Посчитай длину промпта в токенах** (грубо: символы × 0.25)
2. **Если >6000 токенов** — удали необязательные части (историю проекта, отладочные примеры)
3. **Оставь только Layer 1 + Layer 5** — они критичны. Layer 2–3 только если задача их реально требует
4. **Используй progressive disclosure**: укажи только ключевые файлы, Codex сам прочитает остальные через `cat` / `grep`

## Pitfalls

- **Не задавай вопросы если пользователь сказал «сделай сам»** — это раздражает. Используй default-значения.
- **Не переспрашивай очевидное.** Если в запросе уже есть «напиши бота на aiogram 3.x» — не спрашивай «на чём писать?».
- **Context Map должна быть компактной.** Не более 10 пунктов в сумме. Детали — в промпт.
- **Codex CLI требует SOCKS5 прокси** для работы из РФ. Команда должна быть обёрнута: `ALL_PROXY=socks5h://127.0.0.1:10808 codex exec ...`
- **Для не-git директорий** нужен флаг `-c skip_git_repo_check=true`
- **Для автоматизации** нужен `--dangerously-bypass-approvals-and-sandbox`
- **Не генерируй промпт длиннее 8000 символов** — Codex теряет контекст. Если больше — разбей на фазы через supergoal.
- **Если задача на русском** — промпт для Codex пиши на русском, кодекс понимает. Но technical terms лучше на английском.

## Когда НЕ использовать TCE

- Задача уже чёткая и конкретная (просто выполни)
- Пользователь просит «просто быстро починить» (выполни без уточнений)
- Одношаговая команда (curl, git, запустить скрипт)
